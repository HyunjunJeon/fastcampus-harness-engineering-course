# 비전공자를 위한 Web Service MVP 개발 과정

웹 서비스 MVP를 만들 때, 개발자가 아닌 사람이 먼저 고민해야 할 질문들입니다.

개발 지식을 많이 외우자는 문서가 아닙니다. 
개발자나 AI 에이전트에게 일을 맡길 때 이 정도는 사람이 직접 확인하자는 쪽에 가깝습니다.

- 이 서비스의 사용자는 무엇을 할 수 있어야 하는가?
- 화면에는 무엇이 보여야 하는가?
- 버튼을 누르면 실제로 어떤 일이 일어나야 하는가?
- 어떤 정보가 저장되어야 하는가?
- 어떤 행동은 막아야 하는가?
- 실패했을 때 사용자는 무엇을 알아야 하는가?
- 완료됐다는 증거는 무엇인가?

이 질문에 답할 수 있으면 비전공자도 MVP 개발을 꽤 완성도 있게 진행할 수 있습니다.

---

## 1. 웹 서비스는 5가지로 나누어 보면 이해하기 쉽다

웹 서비스는 사용자에게는 화면 하나로 보입니다. 
하지만 실제로는 여러 부분이 함께 움직입니다.

처음에는 사용자 관점에서 아래 5가지로 나누어 보면 충분히 이해하기 쉽습니다.

| 구분 | 쉽게 말하면 | 예시 |
| --- | --- | --- |
| 화면 | 사용자가 보고 누르는 부분 | 버튼, 입력창, 목록, 상세 화면 |
| 처리 | 버튼을 눌렀을 때 실제 일을 하는 부분 | 저장하기, 실행하기, 취소하기 |
| 저장 | 서비스가 기억해야 하는 정보를 보관하는 곳 | 사용자, 목표, 작업, 실행 기록 |
| 규칙 | 이 서비스에서 반드시 지켜야 하는 약속 | 예산이 부족하면 실행하지 않기 |
| 안전 | 위험한 행동을 막고 중요한 일을 기록하는 장치 | 로그인, 권한, 승인, 감사 기록 |

개발자와 이야기할 때는 아래 이름을 들을 수 있습니다. 
자세히는 몰라도 되지만, 뜻을 알면 대화가 쉬워집니다.

| 쉬운 이름 | 개발자가 자주 쓰는 말 |
| --- | --- |
| 화면 | 프론트엔드 |
| 처리 | 백엔드, API |
| 저장 | 데이터베이스, DB |
| 규칙 | 비즈니스 로직 |
| 안전 | 보안, 감사 로그 |

화면만 보면 반쪽입니다.
화면이 예뻐도 아래가 빠지면 실제 서비스로 쓰기 어렵습니다.

- 버튼을 눌러도 실제 처리가 안 된다.
- 처리 결과가 저장되지 않는다.
- 사용자가 하면 안 되는 행동을 막지 못한다.
- 실패했는데 이유를 알 수 없다.
- 완료됐다는 증거가 없다.

### 5가지로만 보면 충분한가?

작은 MVP를 이해하고 시작하기에는 충분합니다. 
다만 실제로 만들기 시작하면 위 5가지에 더해 아래 3가지를 꼭 같이 봐야 합니다.

| 추가로 봐야 할 것 | 쉬운 설명 | 확인 질문 |
| --- | --- | --- |
| 범위 | 이번 MVP에서 할 것과 안 할 것 | 지금 꼭 필요한 기능인가? 다음 버전으로 미뤄도 되는가? |
| 확인 | 제대로 만들어졌는지 보는 방법 | 사용자가 직접 확인할 화면이나 테스트 결과가 있는가? |
| 운영 | 실제로 써볼 수 있는 상태인지 확인 | 실행 주소, 오류 기록, 설정값이 준비되어 있는가? |

그래서 MVP는 5가지로 나누어 설계한다.
하지만 완료 판단은 범위, 확인, 운영까지 같이 봐야 한다.

결제, 개인정보, 외부 메시지 발송, 실제 고객에게 공개되는 배포가 들어가면 더 조심해야 합니다. 이 경우에는 법적 책임, 보안 사고, 장애 대응까지 별도로 검토해야 합니다.

## 2. MVP 개발은 이 순서 해보세요.

MVP는 “일단 화면부터 만들자”로 시작하면 중간에 자주 무너집니다.

권장 순서는 아래와 같습니다.

1. 누구를 위한 서비스(사용 대상)인지 정한다.
2. 사용자가 반드시 성공해야 하는 한 가지 메인 서비스 사용 흐름을 정한다.
3. 저장해야 할 정보를 정한다.
4. 반드시 지켜야 할 규칙을 정한다.
5. 필요한 화면을 정한다.
6. 버튼을 눌렀을 때 일어날 처리를 정한다.
7. 막아야 할 행동과 승인할 행동을 정한다.
8. 실패했을 때 보여줄 내용을 정한다.
9. 개발 작업을 작게 나눈다.
10. 제대로 됐다는 증거를 확인한다.
11. 실제로 접속해서 확인한다.

자주 놓치는 부분은 3번부터 8번입니다.

많은 사람이 “화면만 있으면 MVP가 된 것”처럼 생각합니다. 
하지만 실제 서비스는 **저장할 정보와 지켜야 할 규칙**이 먼저 정리되어야 안정적으로 움직입니다.

| 단계 | 남겨야 하는 것 | 왜 필요한가 |
| --- | --- | --- |
| 사용자와 문제 정의 | 누구의 어떤 문제를 푸는지 | 만들지 말아야 할 기능을 걸러낸다 |
| 핵심 흐름 정의 | 사용자의 첫 성공 경험 | 화면, 저장, 처리의 기준이 된다 |
| 저장 정보 정의 | 어떤 기록이 남아야 하는지 | 나중에 결과를 확인할 수 있다 |
| 규칙 정의 | 허용/금지 조건 | 잘못된 실행을 막는다 |
| 화면 정의 | 사용자가 보는 화면 목록 | 개발 범위가 선명해진다 |
| 처리 정의 | 버튼을 누르면 일어나는 일 | 화면과 실제 동작이 연결된다 |
| 안전 정의 | 권한, 승인, 기록 | 사고를 줄인다 |
| 실패 정의 | 실패 메시지와 복구 방법 | 사용자가 다음 행동을 알 수 있다 |
| 확인 정의 | 테스트 결과, 실행 화면, 기록 | 완료 여부를 믿을 수 있다 |

좋은 MVP 개발은 아이디어를 바로 코드로 보내지 않습니다.

먼저 “이번 버전에서 무엇이 되면 성공인가”를 정하고, 그다음 작은 작업으로 나누고, 마지막에 사용자가 볼 수 있는 증거로 확인합니다.

## 3. 가장 먼저 고정할 것: 핵심 흐름

MVP에서 가장 중요한 질문은 “기능을 얼마나 많이 넣을까?”가 아닙니다.

> 사용자가 어떤 행동을 시작해서, 어떤 결과를 보고, 어떤 기록이 남으면 이 서비스가 작동한다고 말할 수 있는가?

여기서는 이것을 **핵심 Workflow**이라고 부르겠습니다.
예를 들어 “AI 작업 관리 서비스”라면 핵심 Workflow에 대한 흐름은 이렇게 잡을 수 있습니다.

1. 사용자가 목표를 만든다.
2. 목표 아래에 작업을 만든다.
3. AI 작업자에게 작업을 맡긴다.
4. AI 작업자가 실행한다.
5. 실행 결과가 저장된다.
6. 사용자는 결과와 비용을 확인한다.
7. 중요한 변경은 기록으로 남는다.

핵심 Workflow은 기능을 얇게 여러 개 깔아두는 일이 아닙니다.
한 가지 기능을 사용하는 Workflow 을 끝까지 만드는 일입니다.

### 핵심 Workflow 은 동작 확인까지 포함해야 진짜 MVP 개발 완료

개발자 입장에서는 “코드를 작성했다”가 중간 완료처럼 보일 수 있습니다. 하지만 비전공자에게 필요한 것은 “정말 작동한다고 믿을 수 있는 근거”입니다.

그래서 핵심 Workflow은 아래처럼 끝나야 합니다.

아이디어 입력
-> 이번 MVP 범위 정리
-> 개발 작업 진행
-> 오류, 저장 정보, 권한 문제 확인
-> 실행 화면 또는 미리보기 주소 확인
-> 완료 증거 정리

미리보기 화면과 완료 증거가 없으면 사용자는 결과를 믿기 어렵습니다.

“코드가 작성됨”은 완료가 아닙니다. 
**사용자가 확인할 수 있는 End-to-End Test 가 되어야지만 완료**입니다.

### 핵심 Workflow을 정할 때 물어볼 질문

| 질문 | 왜 중요한가 |
| --- | --- |
| 첫 사용자는 누구인가? | 화면과 권한이 달라진다 |
| 사용자가 처음으로 성공해야 하는 일은 무엇인가? | MVP 성공 기준이 된다 |
| 어떤 정보가 꼭 저장되어야 하는가? | 나중에 결과를 확인할 수 있다 |
| 어떤 행동은 막아야 하는가? | 사고를 막는다 |
| 실패하면 어디에 보여줘야 하는가? | 사용자가 다음 행동을 알 수 있다 |
| 완료됐다는 증거는 무엇인가? | 개발 완료를 믿을 수 있다 |

### 핵심 Workflow을 문서로 남길 때 들어갈 내용

| 항목 | 예시 |
| --- | --- |
| 사용자가 입력하는 것 | 목표 제목, 성공 기준, 예산 |
| 새로 생기는 기록 | 목표, 작업, 실행 결과, 비용 기록, 변경 기록 |
| 지켜야 하는 규칙 | 예산 부족 시 실행 금지, 승인 전 실행 금지 |
| 마지막 상태 | 작업 완료, 검토 대기, 실패 종료 |
| 사용자가 보는 결과 | 현재 상태, 실행 로그, 비용, 승인 기록 |
| 완료 증거 | 미리보기 주소, 테스트 결과, 생성된 기록 요약 |

## 4. 기능을 만들 때는 “역할별 체크리스트”로 본다

기능 하나를 만들 때 “화면 담당”, “서버 담당”처럼 사람이나 파일 기준으로만 나누면 빈틈이 생깁니다.
**역할별 체크리스트**로 나누는 편이 훨씬 쉽습니다.

| 체크리스트 | 쉬운 질문 | 개발자가 자주 쓰는 말 |
| --- | --- | --- |
| 기획 | 이 기능은 누구에게 왜 필요한가? | 기획, Product |
| 화면 | 사용자는 무엇을 보고 무엇을 누르는가? | 프론트엔드 |
| 처리 | 버튼을 누르면 실제로 어떤 일이 일어나는가? | 백엔드, API |
| 저장 | 어떤 기록이 남아야 하는가? | 데이터베이스, DB |
| 규칙 | 어떤 조건에서는 실행되면 안 되는가? | 비즈니스 로직 |
| 안전 | 누가 할 수 있고, 무엇은 승인받아야 하는가? | 보안 |
| 확인 | 제대로 됐다는 증거는 무엇인가? | 테스트, 완료 증거 |
| 운영 | 실제 주소에서 확인되고, 문제가 나면 추적 가능한가? | 배포, 운영 |

예를 들어 “AI 작업자에게 작업 실행시키기” 기능을 만든다면 이렇게 봅니다.

| 체크리스트 | 확인할 내용 |
| --- | --- |
| 기획 | 사용자가 왜 실행 버튼을 누르는가? 실행되면 무엇이 좋아지는가? |
| 화면 | 실행 버튼, 진행 중 표시, 실패 메시지가 보이는가? |
| 처리 | 버튼을 누르면 실행 기록이 만들어지고 중복 실행이 막히는가? |
| 저장 | 실행 결과, 비용, 로그가 저장되는가? |
| 규칙 | 이미 실행 중이면 다시 실행되지 않는가? |
| 안전 | 예산이 부족하거나 승인이 필요하면 실행 전에 멈추는가? |
| 확인 | 성공한 경우와 실패한 경우를 둘 다 확인했는가? |
| 운영 | 미리보기 주소에서 같은 흐름을 다시 해볼 수 있는가? |

“화면은 있는데 기록이 없다”, “실행은 되는데 실패 이유가 없다”, “권한 없이 위험한 행동이 가능하다” 같은 문제를 체크리스트를 통해서 빨리 찾을 수 있습니다.

### 개발자나 AI Agent 에게 줄 작업 요청 예시

나쁜 요청:

```text
작업 실행 기능 만들어줘.
```

좋은 요청(자세한 것):

```text
작업 실행 기능을 만들어줘.

사용자가 해야 할 일:
- 작업 상세 화면에서 실행 버튼을 누른다.
- 실행 중인지, 성공했는지, 실패했는지 볼 수 있다.

저장되어야 할 것:
- 실행 기록
- 실행 로그
- 비용 기록
- 중요한 변경 기록

막아야 할 것:
- 이미 실행 중인 작업을 또 실행하는 것
- 예산이 부족한데 실행하는 것
- 승인이 필요한 행동을 승인 없이 실행하는 것

완료 증거:
- 미리보기 화면에서 직접 확인 가능
- 성공 사례와 실패 사례 확인
- 생성된 기록 요약 제공
```

이 정도만 적어도 작업 범위가 훨씬 선명해집니다.

## 5. 화면: 사용자가 실제로 만나는 곳

화면은 예쁜 껍데기가 아닙니다.

사용자가 지금 무슨 일이 일어나고 있는지 이해하고, 다음 행동을 안전하게 선택하게 만드는 곳입니다.

### 화면에서 정해야 할 것

| 항목 | 확인 질문 |
| --- | --- |
| 화면 목록 | 어떤 화면이 필요한가? |
| 이동 흐름 | 사용자는 어떤 순서로 이동하는가? |
| 입력값 | 사용자가 무엇을 입력해야 하는가? |
| 상태 표시 | 진행 중, 성공, 실패, 비어 있음이 보이는가? |
| 위험 표시 | 비용, 삭제, 권한 변경처럼 조심할 행동이 드러나는가? |
| 버튼 결과 | 버튼을 누르면 무엇이 생기거나 바뀌는가? |
| 권한 차이 | 할 수 없는 행동은 어떻게 보이는가? |

### MVP 화면 체크리스트

| 화면 | 확인 질문 |
| --- | --- |
| 첫 화면 | 지금 진행 중인 일이 한눈에 보이는가? |
| 목표 상세 | 목표, 연결된 작업, 비용, 상태가 보이는가? |
| 작업 상세 | 실행 버튼, 실행 결과, 실패 이유가 보이는가? |
| 승인 대기 화면 | 왜 승인이 필요한지 보이는가? |
| 오류 화면 | 실패했을 때 다음 행동을 알 수 있는가? |
| 빈 화면 | 데이터가 없을 때 무엇을 해야 할지 알려주는가? |

### 화면에서 흔한 실수

| 실수 | 왜 문제인가 |
| --- | --- |
| 성공 화면만 만든다 | 실패했을 때 제품이 깨져 보인다 |
| 버튼만 있고 결과가 없다 | 사용자는 실행됐는지 알 수 없다 |
| 위험한 행동이 평범한 버튼처럼 보인다 | 삭제, 비용, 권한 사고가 생길 수 있다 |
| 실제 상태와 화면 상태가 다르다 | 사용자가 서비스를 믿기 어렵다 |
| 첫 버전에 화면을 너무 많이 넣는다 | 핵심 흐름 완성이 늦어진다 |

---

## 6. 처리: 버튼을 눌렀을 때 실제 일을 하는 곳

사용자가 버튼을 누르면 화면 뒤에서는 실제 처리가 일어납니다.

예를 들어 “실행” 버튼을 누르면 아래 일이 일어날 수 있습니다.

```text
1. 사용자가 실행 버튼을 누른다.
2. 실행해도 되는 상태인지 확인한다.
3. 권한과 예산을 확인한다.
4. 실행 기록을 만든다.
5. 실제 작업을 시작한다.
6. 결과를 저장한다.
7. 사용자에게 결과를 보여준다.
```

이 부분을 개발자들은 보통 백엔드 또는 API라고 부릅니다.

### 처리 쪽에서 반드시 해야 할 일

| 책임 | 쉬운 설명 |
| --- | --- |
| 요청 받기 | 사용자가 누른 버튼의 요청을 받는다 |
| 입력 확인 | 이상한 값이나 빠진 값이 없는지 확인한다 |
| 권한 확인 | 이 사용자가 이 행동을 해도 되는지 확인한다 |
| 규칙 확인 | 예산, 상태, 승인 조건을 확인한다 |
| 기록 변경 | 필요한 정보를 새로 만들거나 수정한다 |
| 실패 응답 | 실패한 이유를 같은 형식으로 알려준다 |
| 중요 기록 | 중요한 변경은 나중에 볼 수 있게 남긴다 |

### 처리 쪽에서 꼭 막아야 하는 것

| 상황 | 해야 할 일 |
| --- | --- |
| 예산이 부족함 | 실행 전에 멈춘다 |
| 승인이 필요함 | 승인 요청을 만들고 실행은 보류한다 |
| 권한이 없음 | 실행하지 않고 이유를 기록한다 |
| 이미 실행 중임 | 중복 실행을 막는다 |
| 이미 종료된 대상을 다시 실행하려 함 | 거부한다 |
| 결과가 이상하게 돌아옴 | 실패 상태로 닫고 이유를 남긴다 |
| 비밀값이 결과에 섞임 | 저장하거나 보여주기 전에 가린다 |

화면에서 버튼을 숨기는 것만으로는 충분하지 않습니다.

**최종 방어선은 처리 쪽에 있어야 합니다.**

---

## 7. 저장: 서비스가 기억해야 할 사실

저장은 단순히 데이터를 넣어두는 곳이 아닙니다.

서비스가 “사실”이라고 믿는 내용을 보관하는 곳입니다. 화면은 나중에 바뀔 수 있지만, 저장된 기록이 틀리면 서비스 전체가 흔들립니다.

### 저장 설계의 기본 원칙

| 원칙 | 쉬운 설명 |
| --- | --- |
| 중요한 대상을 따로 기록한다 | 목표, 작업, 실행, 비용, 변경 기록 |
| 관계를 분명히 한다 | 어떤 작업이 어떤 목표에 속하는지 알아야 한다 |
| 상태를 정해둔다 | 대기 중, 실행 중, 실패, 완료처럼 정해진 말만 쓴다 |
| 중요한 변경은 남긴다 | 누가 언제 무엇을 바꿨는지 볼 수 있어야 한다 |
| 비용은 따로 남긴다 | 나중에 합계와 경고를 만들 수 있어야 한다 |
| 삭제보다 보관을 우선한다 | 실수했을 때 되돌리거나 확인할 수 있어야 한다 |

### MVP에서 자주 필요한 기록

| 기록 | 역할 |
| --- | --- |
| 사용자 또는 작업 공간 | 누가 사용하는지 |
| 목표 | 사용자가 달성하려는 것 |
| 작업 | 목표를 이루기 위해 해야 할 일 |
| 실행 | 작업을 실제로 돌린 기록 |
| 실행 로그 | 실행 중 또는 실행 후 남은 메시지 |
| 비용 기록 | 실행에 든 비용 |
| 승인 기록 | 사람이 승인했는지 |
| 변경 기록 | 중요한 변경의 흔적 |

### 저장에서 흔한 실수

| 실수 | 결과 |
| --- | --- |
| 상태를 아무 말로나 저장한다 | 코드마다 다른 표현을 쓰게 된다 |
| 관계를 느슨하게 둔다 | 어떤 실행이 어떤 작업의 결과인지 추적하기 어렵다 |
| 변경 기록을 나중에 붙인다 | 사고가 났을 때 원인을 알 수 없다 |
| 쉽게 완전 삭제한다 | 사용자 실수나 AI 실수를 되돌리기 어렵다 |
| 비용을 아무 곳에나 섞어둔다 | 합계와 경고를 만들기 어렵다 |

---

## 8. 규칙: 이 서비스에서 반드시 지켜야 하는 약속

규칙은 “이 제품에서 반드시 지켜야 하는 판단 기준”입니다.

예를 들어 아래는 모두 규칙입니다.

- 멈춘 목표에서는 새 작업을 실행할 수 없다.
- 비활성화된 AI 작업자에게는 일을 맡길 수 없다.
- 하나의 작업은 동시에 두 번 실행되면 안 된다.
- 예산이 부족하면 실행하면 안 된다.
- 위험한 행동은 승인 없이 실행하면 안 된다.
- 비밀값은 화면이나 기록에 그대로 남기면 안 된다.

이 규칙을 화면에만 두면 위험합니다.

사용자가 주소를 직접 호출하거나 AI가 잘못된 요청을 보내도 규칙이 지켜져야 합니다. 그래서 중요한 규칙은 처리 쪽에서 다시 확인해야 합니다.

### 규칙 체크리스트

| 질문 | 예시 |
| --- | --- |
| 이 행동은 언제 가능한가? | 작업이 대기 중일 때만 실행 가능 |
| 행동 후 상태는 어떻게 바뀌는가? | 대기 중 -> 실행 중 -> 완료 또는 실패 |
| 실패하면 어떤 상태가 되는가? | 실행 중 -> 실패 |
| 어떤 기록이 반드시 생기는가? | 실행 기록, 로그, 변경 기록 |
| 어떤 행동은 승인 전 금지인가? | 비용 발생, 외부 발송, 대량 변경 |
| 어떤 행동은 절대 허용하면 안 되는가? | 종료된 대상을 다시 살리는 행동 |

---

## 9. 안전: 나중에 붙이는 기능이 아니라 처음부터 필요한 장치

안전은 로그인 화면만 뜻하지 않습니다.

MVP라도 최소한의 안전장치는 처음부터 필요합니다.

### MVP에서 필요한 안전장치

| 영역 | 쉬운 설명 |
| --- | --- |
| 사용자 확인 | 누가 행동했는지 알 수 있어야 한다 |
| 권한 확인 | 이 사용자가 이 행동을 해도 되는지 확인해야 한다 |
| 승인 | 위험한 행동은 사람의 확인을 받아야 한다 |
| 비밀값 보호 | API key, token 같은 접근 열쇠가 화면이나 로그에 나오면 안 된다 |
| 입력값 확인 | 이상한 값이나 위험한 요청을 거부해야 한다 |
| 변경 기록 | 중요한 변경은 기록으로 남겨야 한다 |
| 예산 보호 | 비용이 부족하면 실행 전에 막아야 한다 |

### 사람 승인이 필요한 행동

아래 행동은 AI가 판단했더라도 사람에게 확인받는 편이 안전합니다.

| 행동 | 왜 조심해야 하나 | 승인 전에는 무엇까지 가능한가 |
| --- | --- | --- |
| 비용 발생 | 실제 돈이 나갈 수 있다 | 예상 비용 계산, 실행 계획 작성 |
| 기존 데이터 대량 변경 | 되돌리기 어려울 수 있다 | 영향 범위 확인, 백업 계획 작성 |
| 실제 서비스 배포 | 사용자에게 장애가 보일 수 있다 | 미리보기 배포, 테스트 |
| 비밀값 사용 | 권한이 새어 나갈 수 있다 | 필요한 권한 설명 |
| 권한 확대 | AI가 더 위험한 행동을 할 수 있다 | 필요한 권한 목록 정리 |
| 외부 발송 | 이메일, Slack, 결제 알림이 실제로 나갈 수 있다 | 메시지 초안 작성, 수신자 확인 |

반대로 문서 작성, 작업 쪼개기, 가짜 데이터로 화면 만들기, 로컬 테스트, 미리보기 확인, 실패 로그 해석은 보통 자동으로 진행해도 됩니다.

사람을 매번 붙잡자는 얘기가 아닙니다.

**멈춰야 할 순간에만 확실히 멈추자는 것**입니다.

---

## 10. 실패 처리는 기능보다 먼저 생각한다

개발 계획에서 가장 자주 빠지는 부분이 실패 처리입니다.

성공 흐름은 대부분 비슷합니다. 서비스의 품질은 실패했을 때 드러납니다.

### 실패 상황 예시

| 실패 상황 | 서비스가 해야 할 일 | 사용자에게 보여줄 것 |
| --- | --- | --- |
| 예산 부족 | 실행 전 멈춘다 | 필요한 예산과 현재 잔액 |
| 승인 필요 | 승인 요청을 만들고 대기한다 | 왜 승인이 필요한지 |
| 권한 없음 | 실행하지 않는다 | 어떤 권한이 부족한지 |
| 실행 시간 초과 | 실패로 닫고 재시도 가능하게 한다 | 얼마나 기다렸고 다시 할 수 있는지 |
| 작업자 오류 | 기존 상태를 망가뜨리지 않는다 | 오류 이유와 복구 방법 |
| 중복 실행 | 새 실행을 만들지 않는다 | 이미 실행 중인 작업 |

### 실패 처리의 원칙

```text
실패는 조용히 사라지면 안 된다.
실패는 상태, 기록, 사용자 메시지로 닫혀야 한다.
```

사용자에게 “실패했습니다”만 보여주는 것도 부족합니다.

좋은 실패 메시지는 아래 세 가지를 알려줍니다.

- 무엇이 실패했는가?
- 왜 실패했는가?
- 사용자는 다음에 무엇을 하면 되는가?

## 11. 복잡도를 낮추는 방법

여기서 말하는 복잡도는 “한 번에 이해해야 하는 것의 양”입니다.

복잡도가 높아지면 개발자도, AI도, 사용자도 실수합니다.

### 복잡한 기능인지 판단하는 간단한 점수표

아래 항목이 하나 들어갈 때마다 1점을 더합니다.

| 항목 | 예시 |
| --- | --- |
| 새 화면이 필요하다 | 작업 상세 화면 |
| 새 버튼이나 입력창이 필요하다 | 실행 버튼, 예산 입력 |
| 새 기록이 저장되어야 한다 | 실행 기록, 비용 기록 |
| 상태가 바뀐다 | 대기 중 -> 실행 중 -> 완료 |
| 권한이나 승인이 필요하다 | 관리자만 가능, 사람 승인 필요 |
| 돈이 들거나 외부로 발송된다 | 결제, 이메일, Slack |
| 자동 실행이나 대기 시간이 있다 | AI 실행, 예약 작업 |
| 실패 상황을 따로 처리해야 한다 | 시간 초과, 예산 부족, 권한 없음 |

점수는 정확한 수학이 아닙니다. 작업을 작게 나누기 위한 기준입니다.

| 점수 | 판단 | 진행 방법 |
| --- | --- | --- |
| 0~3점 | 작은 작업 | 한 번에 진행해도 된다 |
| 4~6점 | 중간 작업 | 화면, 처리, 저장, 확인을 나누어 진행한다 |
| 7점 이상 | 큰 작업 | 먼저 문서로 정리한 뒤 나누어 개발한다 |

특히 아래가 들어가면 점수가 낮아도 조심해야 합니다.

- 돈이 나간다.
- 데이터를 많이 바꾼다.
- 외부로 메시지가 나간다.
- 비밀값을 사용한다.
- 실제 사용자에게 공개된다.

### 복잡도를 낮추는 실전 규칙

| 규칙 | 예시 |
| --- | --- |
| 한 작업에는 중요한 행동 하나만 넣는다 | 목표 만들기와 작업 실행을 한 번에 묶지 않는다 |
| 상태 변화는 표로 먼저 쓴다 | 대기 중 -> 실행 중 -> 완료/실패 |
| 실패 상황을 성공 상황 옆에 같이 둔다 | 성공, 예산 부족, 권한 없음, 시간 초과 |
| 위험한 행동은 이름부터 분명히 한다 | 삭제, 배포, 외부 발송, 권한 변경 |
| 완료 증거를 미리 정한다 | 화면 캡처, 실행 기록, 비용 기록, 테스트 결과 |
| 다음 버전으로 미룰 것을 적는다 | 다중 사용자, 결제, 외부 연동 등 |

### 나쁜 작업 요청과 좋은 작업 요청

나쁜 요청:

```text
대시보드 전체 만들어줘.
```

좋은 요청:

```text
대시보드에서 현재 진행 중인 작업 목록만 먼저 보여줘.

포함할 것:
- 작업 이름
- 현재 상태
- 마지막 실행 시간
- 실패한 경우 실패 이유

이번에 제외할 것:
- 통계 그래프
- 사용자 설정
- 결제 정보
- 알림 기능

완료 증거:
- 작업이 없는 경우 화면
- 작업이 있는 경우 화면
- 실패한 작업이 있는 경우 화면
```

좋은 요청은 범위를 줄입니다. 범위가 줄어야 결과를 확인하기 쉽습니다.

## 12. 구현 작업을 작게 나누는 예시

MVP를 한 번에 만들려고 하면 범위가 너무 커집니다. 아래처럼 작은 단계로 나누는 편이 안전합니다.

| 순서 | 목표 | 완료 기준 |
| --- | --- | --- |
| 1 | 기본 화면과 이동 흐름 만들기 | 사용자가 주요 화면을 이동할 수 있다 |
| 2 | 저장할 정보 정리 | 목표, 작업, 실행 기록이 저장된다 |
| 3 | 목표와 작업 만들기 | 사용자가 목표와 작업을 만들 수 있다 |
| 4 | 상태 변화 정리 | 대기 중, 실행 중, 완료, 실패가 구분된다 |
| 5 | 실행 기능 만들기 | 작업을 실행하고 결과가 남는다 |
| 6 | 가짜 실행으로 먼저 확인 | 실제 AI 연결 전에도 흐름을 볼 수 있다 |
| 7 | 예산과 승인 막기 | 위험한 실행이 시작 전에 멈춘다 |
| 8 | 로그와 실패 이유 보여주기 | 실패했을 때 이유를 볼 수 있다 |
| 9 | 변경 기록 보여주기 | 누가 언제 무엇을 바꿨는지 볼 수 있다 |
| 10 | 미리보기에서 전체 흐름 확인 | 사용자가 핵심 흐름을 직접 해볼 수 있다 |

각 단계의 완료 기준은 “화면이 보인다”에서 끝나면 안 됩니다.

**화면, 처리, 저장, 실패 처리, 완료 증거**가 함께 확인되어야 합니다.

## 13. 완료는 증거(Evidence)로 판단한다

MVP 개발에서 “작업했습니다”는 완료가 아닙니다.
완료는 사용자가 직접 확인할 수 있고, 실패했을 때 원인을 추적할 수 있는 상태입니다.

### 완료 시 받아야 하는 결과물(증거)

| 결과물(증거) | 확인할 내용 |
| --- | --- |
| 미리보기 주소 또는 실행 화면 | 사용자가 핵심 흐름을 직접 볼 수 있는가 |
| 테스트 결과 | 기본 확인 명령이 통과했는가 |
| 생성된 기록 요약 | 어떤 목표, 작업, 실행 기록이 생겼는가 |
| 상태 변화 요약 | 어디서 시작해 어떤 상태로 끝났는가 |
| 실패 확인 | 예산 부족, 권한 없음, 시간 초과 같은 실패가 확인됐는가 |
| 남은 위험 | 이번 MVP에서 일부러 제외한 것은 무엇인가 |

### 완료로 인정하면 안 되는 경우

| 상황 | 이유 |
| --- | --- |
| 코드만 있고 화면 확인이 없다 | 사용자가 결과를 확인할 수 없다 |
| 성공한 경우만 확인했다 | 실패했을 때 제품이 깨질 수 있다 |
| 저장된 기록 확인이 없다 | 화면만 맞고 실제 데이터가 틀릴 수 있다 |
| 변경 기록 확인이 없다 | 사고가 났을 때 원인을 알 수 없다 |
| 테스트 결과가 없다 | 완료 선언을 믿을 근거가 부족하다 |
| 남은 위험을 숨긴다 | 다음 작업자가 같은 문제를 다시 밟는다 |

MVP의 최종 결과물은 단순한 코드가 아닙니다.

미리보기 화면
+ 테스트 결과
+ 생성된 기록
+ 실패 확인
+ 남은 위험

이렇게 묶어서 받아야 합니다.

## 14. 개발 전 최종 체크리스트

개발을 시작하기 전에 개발자는 반드시 아래 질문에 답할 수 있어야 합니다.

### 사용자와 범위

| 질문 | 답변 |
| --- | --- |
| 첫 사용자는 누구인가? | 예: 혼자 쓰는 관리자 |
| 첫 성공 경험은 무엇인가? | 목표 만들기 -> 작업 만들기 -> 실행 -> 결과 확인 |
| 이번 버전에서 제외할 것은 무엇인가? | 다중 사용자, 결제, 외부 알림 등 |

### 화면

| 질문 | 답변 |
| --- | --- |
| 꼭 필요한 화면은 몇 개인가? | 첫 화면, 목표 상세, 작업 상세 등 |
| 각 화면의 가장 중요한 버튼은 무엇인가? | 만들기, 실행하기, 승인하기 |
| 실패, 빈 화면, 진행 중 화면이 준비되어 있는가? | 예/아니오 |

### 처리

| 질문 | 답변 |
| --- | --- |
| 버튼을 누르면 실제로 어떤 일이 일어나는가? | 기록 생성, 상태 변경, 실행 시작 |
| 모든 중요한 변경이 기록되는가? | 예/아니오 |
| 실패 이유가 같은 방식으로 전달되는가? | 예/아니오 |

### 저장

| 질문 | 답변 |
| --- | --- |
| 어떤 기록이 꼭 남아야 하는가? | 목표, 작업, 실행, 비용, 변경 기록 |
| 상태값이 정해져 있는가? | 대기 중, 실행 중, 완료, 실패 |
| 기록 사이의 관계가 분명한가? | 목표 아래 작업, 작업 아래 실행 |

### 안전

| 질문 | 답변 |
| --- | --- |
| 비밀값은 어디에 보관되는가? | 화면이나 로그에 직접 노출하지 않음 |
| 권한 없는 행동은 어디서 막는가? | 처리 쪽에서 막음 |
| 예산과 승인은 실행 전에 확인되는가? | 예/아니오 |

### 규칙

| 질문 | 답변 |
| --- | --- |
| 어떤 상태에서 실행할 수 있는가? | 대기 중인 작업만 실행 가능 |
| 어떤 실패는 다시 시도할 수 있는가? | 시간 초과, 일시적 오류 등 |
| 어떤 행동은 절대 허용하지 않는가? | 종료된 대상을 다시 실행하기 등 |

### 완료 증거

| 질문 | 답변 |
| --- | --- |
| 어디서 직접 확인할 수 있는가? | 미리보기 주소 또는 로컬 실행 화면 |
| 어떤 확인을 통과해야 하는가? | 테스트, 핵심 흐름 확인 |
| 어떤 기록을 확인해야 하는가? | 실행 기록, 비용 기록, 변경 기록 |
| 남은 위험은 어디에 적는가? | 완료 요약, 다음 작업 목록 |
