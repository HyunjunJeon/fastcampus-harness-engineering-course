# Session 3-2 - 사람과 AI가 함께 일하는 Git Repository 운영 규칙

> Git은 개발자만 쓰는 도구가 아니라, AI Agent 가 바꾼 내용을 증거로 남기는 변경 기록입니다.

- AI 작업 전, 작업 중, 작업 후 규칙을 만듭니다.
- 브랜치, 커밋, 리뷰, 문서 동기화, 승인 기준을 하나의 운영 규칙으로 묶습니다.
- 완료 보고에는 변경 파일, 검증 결과, 남은 위험을 포함하게 합니다.

## 진행 흐름

1. Git 저장소를 "공유 문서함의 변경 기록"으로 소개합니다.
2. AI가 만든 변경도 기록과 검토가 필요하다는 점을 설명합니다.
3. 작업 전, 작업 중, 작업 후 규칙을 나누어 작성합니다.
4. AI에게 Claude Code와 Codex에서 각각 어디에 규칙을 둘지 정리하게 합니다.
5. 완료 보고 형식을 만들고, 위험 작업 승인 기준을 마지막으로 확인합니다. 마지막에는 한 줄을 못 박습니다 — "AI 리뷰는 보조이고, 머지를 막을 권한은 CI에 있다."

## Claude Code를 쓴다면

Claude Code와 함께 일할 때는 `CLAUDE.md`, Settings, Hooks, Skills에 규칙을 나누어 둡니다. 예를 들어 작업 전 계획은 `CLAUDE.md`, 반복 검토는 Skill, 위험 명령은 Settings와 Hook으로 분리할 수 있습니다.

Git 변경사항은 Claude의 설명만 믿지 말고 실제 diff 또는 변경 파일 목록으로 확인합니다.

## Codex를 쓴다면

Codex에서는 `AGENTS.md`, Skills, Hooks, Rules를 함께 사용해 운영 규칙을 배치합니다. Rules는 sandbox 밖 명령 실행 기준을 좁혀 적는 용도로 설명합니다. Codex App에서는 리뷰 화면을, CLI에서는 `git status`와 `git diff`를 변경 증거로 사용합니다.

비개발자에게는 Git을 "공유 문서함의 변경 기록"으로 설명하면 이해가 쉽습니다.

## 자주 하는 실수

| 이렇게 하지 않기 | 이렇게 바꾸기 |
|---|---|
| AI 설명만 보고 완료 판단 | diff, 테스트, 문서 확인 증거를 보기 |
| 모든 작업을 main에서 바로 진행 | 브랜치 또는 샘플 저장소에서 실습 |
| commit 메시지를 AI에게만 맡기기 | 사람이 이해할 수 있는 업무 언어로 확인 |
| push와 배포를 자동 허용 | 사람 승인 필요 항목으로 분리 |

## 실습

실습 레포 위치: `part4/lab/CLAUDE.md`, `part4/lab/AGENTS.md`, `part4/lab/.github/workflows/verify.yml`

운영 규칙은 세 곳에 같은 모양으로 둡니다.

- `CLAUDE.md` / `AGENTS.md` — Claude Code와 Codex가 매 세션 자동으로 읽는 규칙.
- 로컬 훅 (`scripts/agent_verify.sh`) — 작업 중·종료 시점에 같은 검증 실행.
- CI required status check (`.github/workflows/verify.yml`) — 사람의 직접 push까지 잡는 최종 게이트.

AI가 만든 PR에는 본문에 명시합니다.

```text
Generated by Claude Code (or Codex)
- Skill used: pr-review
- Verify: bash scripts/agent_verify.sh (passed locally)
- Docs updated: docs/api-contract.md
```

### 머지 게이트는 GitHub Rulesets로 잠근다

우리는 **AI 액션을 required로 걸어 머지를 막지 않습니다**. AI 액션은 토큰·모델 가용성·릴리즈 변경에 영향받기 때문에, 그것을 required로 걸면 거버넌스가 AI 가용성에 종속됩니다. 대신 **GitHub Rulesets**에서 우리 결정적 검증 잡과 보호 규칙을 직접 거는 방식이 안전합니다 — 사람이든 AI든, Claude든 Codex든, 같은 게이트를 통과하게 됩니다.

촬영일 기준 GitHub Rulesets에서 우리 강의에 필요한 6가지 방어:

| 룰 | 무엇을 막는가 | 우리 적용 |
|---|---|---|
| **Require a pull request before merging** | main 등 보호 브랜치에 직접 push 차단 | 모든 변경은 PR 경유 |
| **Require status checks to pass before merging** | CI 미통과 PR 머지 차단 | `verify` 잡을 required로 등록 |
| **Block force pushes** | 기록 덮어쓰기 차단 (기본 활성) | 그대로 활성 유지 |
| **Restrict deletions** | 브랜치 삭제 차단 (기본 활성) | 보호 브랜치에 적용 |
| **Restrict file paths** (또는 **Restrict file extensions**) | `.env`, secrets 파일 변경 자체를 차단 | `.env*`, `*.pem`, `secrets/**` 패턴 등록 (최대 200항목) |
| **Require signed commits** (옵션) | 신원 확인된 커밋만 허용 | 조직 정책에 따라 |

우리 워크플로우의 잡 ID가 `verify`이므로, "Require status checks to pass"에서 같은 이름(`verify`)으로 찾아 required로 켜면 됩니다. Branch protection rule을 쓰는 조직도 같은 옵션이 있으므로 동일하게 적용 가능합니다.

자세한 적용 가이드와 권장 ruleset JSON은 `part4/lab/.github/RULESETS.md`를 참고하세요.

### AI 액션은 어디에 두는가

`anthropics/claude-code-action@v1` 같은 AI 액션은 우리 구조에서 **"보조 리뷰 장치"** 자리에 둡니다. 머지를 막는 게이트(=required status check)에는 두지 않고, PR에 코멘트를 다는 보조 잡으로만 운영합니다. 같은 잡이 토큰 부족이나 모델 장애로 잠시 실패해도 머지는 그대로 가능합니다.

옛 블로그를 참고할 때는 한 가지만 주의하세요 — `@beta` 시절의 인풋(`mode`, `direct_prompt`, `custom_instructions`)이 v1에서는 `prompt`/`claude_args`로 통합되었습니다. 그래서 강의에서 코드를 시연할 때는 "`@v1` + `prompt` + `claude_args`" 세 줄만 짚고, 그 외 옵션은 공식 문서 링크로 넘깁니다. `prompt:`는 `/skill-name` 형태의 스킬 호출도 받으므로 챕터 1의 스킬을 CI에서도 그대로 부를 수 있습니다.

Codex 쪽 `openai/codex-action`은 촬영일 기준 안정 릴리즈 태그가 없습니다(GitHub releases API `null` 반환). 강의에서 단정적인 태그로 시연하지 말고, 공식 문서와 레포 README를 운영일에 다시 확인한다고 안내합니다.

### 시연 동선 요약

1. PR 하나 만들어 일부러 검증을 실패시키고, **Rulesets의 required status check** 때문에 머지가 막히는 화면을 보여준다.
2. 같은 PR에 `@claude` 멘션을 달아 보조 리뷰 코멘트가 달리는 모습을 보여준다 — 단 그 리뷰는 머지 결정에 권한이 없음을 함께 강조한다.
3. `.env` 파일을 일부러 추가한 PR을 만들어 **Restrict file paths** 룰로 push 자체가 막히는 화면을 보여준다.

이 3단계 시연이 "사람·AI 모두에게 같은 정책 게이트"라는 메시지를 손에 잡히게 만듭니다.
