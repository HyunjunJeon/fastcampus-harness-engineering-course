# Session 3-3 - AI가 틀렸을 때 정확히 고치는 질문 패턴

> "아니야, 다시 해봐"라고 말하면 대개 더 나빠집니다.  
> 정답으로 가는 길은 두 단계입니다.  
> ① `증상·재현·기대·실제·제약` 다섯 항목으로 **오답의 발산을 멈춥니다**  
> ② 그 위에서 **가설 3개 + 가설별 검증 명령**으로 정답에 좁혀 들어갑니다  

디버깅 요청은 5개의 주요 주제로 시작합니다. 각 항목은 서로 다른 역할을 합니다.

- **증상(Symptom)** — "무엇이 잘못 보이는가". 한 줄로 압축.
- **재현(Repro)** — "어떤 명령/입력에서". 복붙 가능한 형태.
- **기대(Expected)** — "원래 어떻게 동작해야 하는가". 비즈니스/스펙 기준.
- **실제(Actual)** — 터미널·IDE 출력 **원문 그대로**. 가장 자주 손상되는 항목.
- **제약(Constraints)** — 버전·OS·환경 변수·이전 시도. **가장 자주 누락되는 항목**, 누락되면 가설이 엉뚱한 곳을 가리킴.

- `실제` 항목에는 에러 메시지와 stack trace를 요약하지 말고 원문 그대로 붙입니다. 한국어 요약은 LLM이 강하게 의존하는 정형 신호(파일 경로, 라인 번호, exception 클래스 이름)를 지워버립니다.
- AI에게 바로 수정하게 하지 말고, 원인 가설을 최소 2-3개정도 받습니다.
- 가설은 서로 다른 검증 명령으로 구분 가능해야 합니다. "어떻게 틀렸음을 알 수 있는가?"가 동반되지 않은 가설은 가설이 아니라 추측입니다.

## 진행 흐름

1. 실패한 AI 응답을 `증상/재현/기대/실제/제약`로 다시 적습니다. 이때 `실제`에는 터미널·IDE 출력을 잘라내지 말고 그대로 붙이고, 길면 임의 요약 대신 `--- 중략 ---`으로 명시적으로 잘라냅니다.
2. 그대로 AI에게 주고, "수정하지 말고 원인 가설 세 개와 **가설별로 서로 다른 1분 이내 검증 명령**을 함께 말해 달라"고 요청합니다. 가설마다 "이게 원인이면 X 출력, 아니면 Y 출력"이 나오도록 강제합니다.
3. 가장 가능성 높은 가설 하나만 골라 최소 수정으로 시도하고, 그 가설에 묶인 검증 명령을 다시 돌립니다.
4. 시도한 가설이 틀렸다면 그 시도를 컨텍스트에 남겨두되, 왜 틀렸는지 꼼꼼하게 가이드합니다.

## 잘못된 시도는 컨텍스트의 독이 됩니다

실패한 가설을 같은 대화창에 쌓아두면, 다음 응답은 그 실패에 **앵커링**되어 같은 방향으로 발산합니다. 두 가지 선택지가 있습니다.

- **남긴다면**: 왜 틀렸는지 한 줄로 명시 ("X 출력이 나와야 했는데 Y가 나왔으므로 가설 1 기각").
- **버린다면**: `/rewind`로 시도 직전으로 되돌리거나, 새 세션에서 정리된 5가지 항목만 다시 전달.

**같은 가설을 두 번 반복하지 않게 컨텍스트 내에 '잘못 되었고 왜 잘못된건지' 전달하는 것이 중요**

## Claude Code를 쓴다면

Claude Code에서 잘못 흘러간 대화를 살리는 가장 빠른 방법은 컨텍스트를 정리하는 것입니다. 작업 직전 상태로 되돌아갈 수 있는 명령(`/rewind` 등)을 알아두면, 실패한 가설을 컨텍스트에 쌓지 않고 새로운 가설로 다시 시작할 수 있습니다.

또 한 가지 효과적인 방법은 "다른 새 세션에서 처음 보는 사람처럼 이 코드를 리뷰해 달라"는 두 번째 Claude 호출입니다. 

## Codex를 쓴다면

Codex에서도 같은 원칙이 통합니다. `증상/재현/기대/실제/제약` 다섯 항목을 작업 본문 상단에 적고, 
"원인 가설 3개와 가설별로 구분되는 1분 이내 검증 명령을 먼저 말하라"는 문장을 마지막 줄에 둡니다.

Codex 슬래시 명령 중 `/review`는 같은 변경을 다른 시선으로 다시 확인할 때 유용합니다. 

## 자주 하는 실수

| 이렇게 하지 않기 | 이렇게 바꾸기 |
|---|---|
| "왜 안 돼?"라고만 묻기 | 증상·재현·기대·실제·제약 다섯 항목 채우기 |
| 에러를 한국어로 요약해서 전달하기 | stack trace·exception 클래스·파일:라인을 원문 그대로 붙이기 |
| 가설 없이 바로 수정 부탁 | 가설 3개와 가설별 검증 명령을 먼저 받기 |
| "race condition일 수도" 같은 검증 불가 가설 수용 | "이게 원인이면 X 출력, 아니면 Y 출력"이 나오는 가설만 채택 |
| 실패한 시도를 컨텍스트에 그대로 두기 | 실패한 시도는 비우고 다음 가설로 가기 |
| 광범위한 리팩터링으로 도망가기 | 가설이 맞는지부터 최소 수정으로 확인 |

# 2) 가설을 골라 최소 수정만 적용
