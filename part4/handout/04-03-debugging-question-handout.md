# Session 4-3 - AI가 틀렸을 때 정확히 고치는 질문 패턴

> "아니야, 다시 해봐"라고 말하면 대개 더 나빠집니다. 증상·재현·기대·실제·제약 다섯 칸으로 다시 묻습니다.

- 디버깅 요청은 5개의 주요 주제(증상/재현/기대/실제/제약)를 프롬프트화 하는 것로 시작합니다.
- AI에게 바로 수정하게 하지 말고, 원인 가설을 최소 2-3개정도 받습니다.
- 잘못된 시도는 컨텍스트에 쌓아두되, 명백하게 왜 틀렸는지를 가이드합니다.

## 진행 흐름

1. 실패한 AI 응답 한 개를 화면에 띄우고, 왜 더 나빠졌는지 함께 살펴봅니다.
2. 같은 문제를 다섯 칸 카드(증상/재현/기대/실제/제약)로 다시 적습니다.
3. 카드를 그대로 AI에게 주고, "수정하지 말고 원인 가설을 세 개 적고 검증 방법까지 말해 달라"고 요청합니다.
4. 가장 가능성 높은 가설 하나만 골라 최소 수정으로 시도하고, 검증 명령을 다시 돌립니다.
5. 시도한 가설이 틀렸다면 그 시도를 컨텍스트에 남겨두되, 왜 틀렸는지 꼼꼼하게 가이드합니다.

## Claude Code를 쓴다면

Claude Code에서 잘못 흘러간 대화를 살리는 가장 빠른 방법은 컨텍스트를 정리하는 것입니다. 작업 직전 상태로 되돌아갈 수 있는 명령(`/rewind` 등)을 알아두면, 실패한 가설을 컨텍스트에 쌓지 않고 새로운 가설로 다시 시작할 수 있습니다.

또 한 가지 효과적인 방법은 "다른 새 세션에서 처음 보는 사람처럼 이 코드를 리뷰해 달라"는 두 번째 Claude 호출입니다. 

## Codex를 쓴다면

Codex에서도 같은 원칙이 통합니다. 다섯 칸 카드를 작업 카드 본문 상단에 적고, "원인 가설 3개와 검증 방법을 먼저 말하라"는 문장을 마지막 줄에 둡니다.

Codex 슬래시 명령 중 `/review`는 같은 변경을 다른 시선으로 다시 확인할 때 유용합니다. 

## 자주 하는 실수

| 이렇게 하지 않기 | 이렇게 바꾸기 |
|---|---|
| "왜 안 돼?"라고만 묻기 | 증상·재현·기대·실제·제약 다섯 칸 채우기 |
| 가설 없이 바로 수정 부탁 | 가설 3개와 검증 방법을 먼저 받기 |
| 실패한 시도를 컨텍스트에 그대로 두기 | 실패한 시도는 비우고 다음 가설로 가기 |
| 광범위한 리팩터링으로 도망가기 | 가설이 맞는지부터 최소 수정으로 확인 |

## 실습

실습 레포 위치: `part4/lab/app/services.py`, `part4/lab/tests/test_notes_api.py`

실패 테스트를 먼저 만든 뒤 가설을 검증합니다. 코드를 먼저 고치지 않는 것이 핵심입니다.

```python
# tests/test_notes_api.py 에 한 줄 추가하는 예시
def test_search_strips_whitespace() -> None:
    service = NotesService()
    service.create(title="hello", body="world")
    assert len(service.search("  hello  ")) == 1
```

```bash
# 1) 테스트가 실패하는지 먼저 확인
pytest -q tests/test_notes_api.py::test_search_strips_whitespace
# 2) 가설을 골라 최소 수정만 적용
# 3) 같은 명령으로 다시 통과 확인
# 4) 마지막에 전체 검증
bash part4/lab/scripts/agent_verify.sh
```

실패가 반복되면 마지막 시도를 컨텍스트에 누적시키지 말고 새 세션 또는 직전 상태로 되돌아가는 것이 빠릅니다. 같은 가설을 두 번 반복하지 않게 적어 두는 것도 도움이 됩니다.
