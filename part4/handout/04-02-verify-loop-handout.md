# Session 4-2 - 테스트·린트·타입체크를 하나의 verify 루프로 묶기

> "가끔 돌려달라"는 부탁 대신, 작업이 끝나는 순간 자동으로 같은 검증 명령이 돌게 합니다.

- 테스트·린트·타입체크·문서 검사를 하나의 진입점으로 묶습니다.
- 같은 진입점을 사람, Claude Code, Codex 로 각각 호출합니다.
- 검증이 실패하면 작업을 강제로 종료시키지 말고, AI에게 다시 일하게 합니다.

## 진행 흐름

1. "어제 잘 되던 코드가 오늘 깨졌다"는 흔한 상황을 함께 떠올립니다.
2. 검증 단계를 종이에 그려, 무엇을 통과해야 "끝"이라 부를 수 있는지 합의합니다.
3. 그 단계들을 한 줄 명령으로 묶을 수 있는지 확인합니다. 도구마다 다른 명령을 외울 필요가 없도록 만듭니다.
4. 그 한 줄을 작업 종료 시점에 자동으로 부르도록 훅에 연결합니다.
5. 일부러 실패하는 변경을 만든 뒤, AI가 검증 실패를 보고 한 번 더 수정 루프를 도는 모습을 함께 확인합니다.

## Claude Code를 쓴다면

Claude Code의 Stop 훅은 작업이 끝나려는 순간에 실행됩니다. 여기서 검증 명령을 부르고, 실패하면 모델이 결과를 보고 한 번 더 수정합니다. "테스트는 통과했어요"라는 말 대신, 실제 실행 결과 텍스트가 모델에게 다시 들어가게 만드는 것이 핵심입니다.

검증 명령은 너무 길어지지 않게 유지합니다. 한 번에 30초~1분 안에 끝나야 모델이 짧은 수정-검증 루프를 돌 수 있습니다.

## Codex를 쓴다면

Codex Stop 훅도 같은 자리에서 검증 명령을 부를 수 있고, 실패 시 Codex가 한 번 더 이어서 작업하도록 신규 프롬프트가 생성됩니다. 촬영일 기준 Codex 훅은 6개 이벤트(SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, Stop)를 중심으로 동작하며, PreToolUse는 Bash와 apply_patch(파일 편집), MCP 도구 호출을 가로챕니다. 단 모든 셸 호출이 잡히는 것은 아니므로, 같은 검증을 Stop 훅과 CI에서 한 번 더 잡는 3중 안전망 패턴을 유지합니다.

검증 명령은 운영체제와 사용자 환경 차이를 줄이기 위해 항상 저장소 안의 같은 파일을 호출하도록 둡니다.


## 자주 하는 실수

| 이렇게 하지 않기 | 이렇게 바꾸기 |
|---|---|
| AI에게 "테스트도 돌려줘"라고 부탁만 하기 | 검증 명령을 훅에 묶어 자동 실행되게 하기 |
| 검증 결과를 AI가 요약해 말하기 | 실제 출력 텍스트를 그대로 받기 |
| 도구마다 다른 검증 명령 외우기 | `agent_verify.sh` 같은 단일 진입점 사용 |
| 실패 시 검증을 약화하기 | 검증을 약화하지 말고 코드를 고치기 |


## Reference

실습 레포 위치: `part4/lab/scripts/agent_verify.sh`, `part4/lab/scripts/stop_verify_hook.py`, `part4/lab/.claude/settings.json`, `part4/lab/.codex/hooks.json`

검증 진입점을 한 곳에 두고 두 도구의 Stop 훅을 같은 래퍼 명령에 연결합니다.

```bash
# 단일 진입점
bash part4/lab/scripts/agent_verify.sh
```

```json
// part4/lab/.claude/settings.json (발췌)
{
  "hooks": {
    "Stop": [{
      "hooks": [{
        "type": "command",
        "command": "python ${CLAUDE_PROJECT_DIR}/scripts/stop_verify_hook.py"
      }]
    }]
  }
}
```

Stop 훅은 `agent_verify.sh`를 직접 호출하지 않고 `stop_verify_hook.py`를 호출합니다. 이 래퍼는 검증이 통과하면 종료 코드 0으로 끝내고, 실패하면 검증 출력을 stderr에 담아 종료 코드 2로 끝냅니다. Claude Code에서는 종료 코드 2가 "아직 멈추지 말고 계속 작업하라"는 신호이고, Codex에서는 같은 신호가 신규 continuation 프롬프트로 바뀝니다. 두 도구 모두 무한 루프 방지를 위해 `stop_hook_active` 같은 입력 필드를 확인해야 하므로, 같은 실패가 반복되면 검증 자체나 요구사항을 의심해야 합니다.

### 한 단계 더 나아가기 — 테스트 에이전트가 훅에서 스킬을 호출하는 회로

지금까지의 검증 루프는 "Stop 훅 래퍼가 셸 스크립트(`agent_verify.sh`)를 부른다" 패턴이었습니다. 하네스 엔지니어링 관점에서 한 단계 더 들어가면, **Claude Code Stop 훅의 `agent` handler 자리에 테스트 전용 에이전트를 두고, 그 에이전트가 우리 스킬을 호출하는** 회로를 만들 수 있습니다. 이 방식은 Claude Code 쪽의 심화·실험 기능으로 소개하고, Codex에서는 현재 같은 역할을 `command` hook 스크립트로 표현합니다. 요즘IT 매거진의 "하네스 엔지니어링"(꼼비, 2026-04)에서는 이 자리를 **Assayer(감정사)** — 테스트 생성·검증을 맡는 에이전트로 명명합니다.

흐름:

1. 작업이 끝나려는 순간 Stop 훅이 발화한다.
2. Claude Code 훅의 `agent` handler가 테스트 에이전트(별도 서브에이전트)를 띄운다.
3. 그 에이전트가 우리 `workflows/debug-loop` 또는 `workflows/doc-sync` 스킬을 자연어로 호출한다.
4. 스킬이 실행한 검증 결과(테스트·문서·정책)를 에이전트가 한 줄로 요약해 메인 컨텍스트로 돌려보낸다.
5. 검증 실패면 메인 에이전트가 다시 수정 루프로 돈다.

이 구조의 가치는 두 가지입니다.

- 검증이 "셸 스크립트의 종료 코드"가 아니라 "에이전트의 판단"이 됩니다. 미묘한 실패(테스트는 통과했지만 동작이 명세와 다른 경우, 또는 docs가 코드와 어긋난 경우)도 잡을 수 있습니다.
- 같은 회로가 Part 5의 멀티 에이전트(역할 분리)로 자연스럽게 확장됩니다. Assayer를 별도 서브에이전트로 분리하면 Part 5의 첫 사례가 됩니다.

> 이 회로의 한 변형인 **Test Driven Generation(TDG) 루프**를 구현할 수 있습니다. 설계 → 테스트 설계 → 테스트 작성 → 코드 작성 → 리팩토링 5개 에이전트의 순차 체이닝, Claude Code 서브에이전트 기반. 단일 에이전트의 검증이 부족할 때 어떤 모양으로 진화시킬 수 있는지의 운영 사례로 들 수 있음. 스킬·훅·정책이 각자 있는 것이 아니라 **서로를 호출하는 자기-구성적 회로**로 묶일 때 하네스가 완성됩니다. "부탁하지 않는다. 환경이 강제한다"
