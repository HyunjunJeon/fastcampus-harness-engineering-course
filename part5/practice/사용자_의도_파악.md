핵심은 **AI가 질문을 많이 하게 만드는 것**이 아니라, 매 턴마다 다음을 반복하게 만드는 것입니다.

> **의도 가설 수립 → 논리학적 질문으로 검증 → 답변을 구조화 → 작업 기록 갱신 → 다음 행동 결정**

소크라테스식 접근은 “상대가 무엇을 믿는지, 왜 그렇게 믿는지 깊이 파고드는 질문”을 중시하고, 실제 체크리스트도 목표, 근거 정보, 추론, 핵심 개념, 가정, 함의, 관점, 맥락을 묻게 합니다. 
요구사항 공학 관점에서도 이해관계자의 니즈를 도출할 때는 기능뿐 아니라 맥락, 생애주기, 품질, 리스크, 우선순위, “왜 필요한가”의 근거를 기록하고 추적해야 합니다. 특히 SEBoK는 rationale, 즉 근거를 묻는 과정이 실제 니즈를 드러내는 데 중요하다고 설명합니다. ([SEBoK][1])

## 1. 먼저 “의도 파악”을 하나의 데이터 구조로 정의해야 합니다

AI가 사용자의 숨은 니즈를 잘 파악하게 하려면, 질문을 하기 전에 **무엇을 채워야 하는지**가 정해져 있어야 합니다. 즉, 모델이 다음과 같은 `Intent Frame`을 계속 업데이트하게 만듭니다.

| 항목        | 의미                       | 예시 질문                                 |
| --------- | ------------------------ | ------------------------------------- |
| 명시 요청     | 사용자가 직접 말한 작업            | “지금 요청하신 산출물은 보고서 초안인가요, 요약본인가요?”     |
| 최종 목적     | 작업을 통해 이루려는 목표           | “이 결과물은 설득, 의사결정, 학습, 실행 중 어디에 쓰이나요?” |
| 대상 독자/사용자 | 결과물을 볼 사람                | “읽는 사람은 임원, 실무자, 고객, 투자자 중 누구인가요?”    |
| 성공 기준     | 잘 끝났다고 판단할 조건            | “어떤 상태가 되면 이 작업이 성공했다고 볼 수 있나요?”      |
| 제약 조건     | 시간, 형식, 톤, 분량, 도구, 정책    | “반드시 지켜야 하는 형식이나 제외해야 할 내용이 있나요?”     |
| 가정        | 사용자가 말하지 않았지만 모델이 추정한 것  | “제가 내부 보고용으로 이해했는데 맞나요?”              |
| 우선순위      | 품질, 속도, 정확성, 창의성, 비용의 순서 | “빠른 초안이 중요한가요, 완성도 높은 결과가 중요한가요?”     |
| 리스크       | 잘못 이해하면 큰 문제가 되는 부분      | “이 부분은 법무/재무/고객 커뮤니케이션에 영향을 주나요?”     |
| 열린 질문     | 아직 확인되지 않은 불확실성          | “결정 전 추가 확인 필요: 대상 독자, 데이터 출처”        |
| 결정 기록     | 사용자가 확정한 사항              | “사용자는 임원 보고용 1페이지 요약을 원함”             |

이 구조가 없으면 AI는 매번 “더 자세히 알려주세요” 같은 모호한 질문을 반복합니다. 반대로 이 구조가 있으면 질문은 **빈칸을 채우기 위한 도구**가 됩니다.

## 2. 질문은 “논리학적 기능”별로 설계해야 합니다

소크라테스식 질문을 AI 작업에 적용할 때는 질문을 감성적으로 만들기보다, 각 질문이 어떤 논리적 역할을 하는지 분류해야 합니다.

| 논리 기능   | 질문 목적            | AI 질문 예시                                                    |
| ------- | ---------------- | ----------------------------------------------------------- |
| 정의 명료화  | 용어의 의미 확정        | “여기서 ‘전문적으로’라는 말은 학술적 엄밀성, 실무 문서 톤, 또는 컨설팅식 구조 중 무엇에 가깝나요?” |
| 목적 확인   | 최종 원인 파악         | “이 작업의 최종 사용처는 내부 판단, 외부 설득, 실행 가이드 중 어디인가요?”               |
| 필요조건 확인 | 반드시 충족해야 할 조건 도출 | “이 결과물에 반드시 포함되어야 하는 요소는 무엇인가요?”                            |
| 충분조건 확인 | 성공 판정 기준 도출      | “어떤 답변을 받으면 ‘이 정도면 충분하다’고 판단하시겠습니까?”                        |
| 가정 검증   | 숨은 전제 확인         | “제가 ‘비전문가 독자’를 기준으로 설명해도 될까요, 아니면 전문가 독자를 전제로 할까요?”         |
| 근거 탐색   | 판단의 기반 확인        | “이 결론을 뒷받침해야 하는 내부 자료나 외부 출처가 있나요?”                         |
| 범위 한정   | 과업 경계 설정         | “이번 작업은 전략 방향까지만 다루나요, 실행 계획까지 포함하나요?”                      |
| 반례 탐색   | 예외 상황 발견         | “이 방식이 적용되면 안 되는 상황이 있나요?”                                  |
| 함의 분석   | 선택의 결과 검토        | “이 방향을 택하면 속도는 빨라지지만 정확도 검증은 약해질 수 있는데 괜찮나요?”               |
| 우선순위 비교 | 충돌하는 가치 정렬       | “정확성, 설득력, 짧은 분량 중 하나만 우선한다면 무엇인가요?”                        |
| 관점 전환   | 이해관계자별 니즈 도출     | “사용자 입장과 의사결정자 입장에서 각각 가장 중요한 점은 무엇일까요?”                    |
| 메타 질문   | 질문 자체의 적절성 검증    | “제가 지금 확인해야 할 질문 중 빠진 것이 있을까요?”                             |

University of Geneva의 소크라테스식 대화 자료도 명료화, 목적, 가정 등을 별도 질문 유형으로 제시합니다. ([Université de Genève][2])

## 3. AI에게는 “질문 생성기”가 아니라 “의도 도출 루프”를 맡겨야 합니다

실무적으로는 다음 루프를 프롬프트나 에이전트 로직으로 고정하는 것이 좋습니다.

### Socratic Intent Elicitation Loop

1. **사용자 발화 분석**
   사용자가 명시적으로 요청한 작업과 암묵적으로 추정되는 목적을 분리합니다.

2. **의도 가설 생성**
   “사용자는 A를 원하는 것 같다”가 아니라, “사용자는 A일 가능성 0.7, B일 가능성 0.3”처럼 가설로 둡니다.

3. **누락 슬롯 탐지**
   목적, 독자, 형식, 성공 기준, 제약, 우선순위 중 비어 있는 항목을 찾습니다.

4. **질문 후보 생성**
   가능한 질문을 여러 개 만들되, 실제로는 가장 정보 가치가 높은 질문만 묻습니다.

5. **질문 선택**
   답변에 따라 결과물이 크게 달라지는 질문, 잘못 이해하면 리스크가 큰 질문, 사용자가 쉽게 답할 수 있는 질문을 우선합니다.

6. **답변 해석 및 기록 갱신**
   답변을 그대로 저장하지 말고, 결정·가정·제약·근거·열린 질문으로 분해합니다.

7. **재확인 또는 실행**
   불확실성이 낮아졌으면 바로 작업하고, 여전히 중요한 모호성이 남았으면 추가 질문합니다.

대화형 AI 연구에서도 사용자의 요구 표현은 정보 비대칭 때문에 불완전하거나 불확실할 수 있고, 안내된 다중 라운드 Q&A가 요구사항 도출에 효과적이라고 봅니다. 다만 질문 라운드가 너무 많으면 사용자 경험이 나빠지므로, 적은 라운드로 정확히 파악하는 정책이 중요합니다. ([arXiv][3])

## 4. 질문을 남발하지 않기 위한 정책이 필요합니다

AI가 논리학적 질문을 하도록 만들면 자칫 “심문형 챗봇”이 됩니다. 그래서 다음 규칙을 두는 것이 좋습니다.

**질문해야 하는 경우**

답변이 없으면 결과물이 크게 달라지는 경우, 되돌리기 어려운 작업인 경우, 법률·의료·재무·브랜드·고객 커뮤니케이션처럼 리스크가 큰 경우, 사용자의 표현이 여러 의미로 해석되는 경우에는 질문해야 합니다.

**질문하지 말아야 하는 경우**

합리적 기본값으로 처리해도 결과 품질에 큰 영향이 없는 경우, 사용자가 빠른 초안을 원한다고 명시한 경우, 질문보다 샘플 초안을 보여주는 편이 더 빠른 경우에는 일단 가정하고 진행한 뒤 확인하는 것이 좋습니다.

질문 선택은 다음처럼 점수화할 수 있습니다.

```text
질문 가치 = 불확실성 × 결과 영향도 × 리스크 × 답변 가능성 - 사용자 부담
```

실무에서는 한 번에 1~3개만 묻는 것이 좋습니다. 질문이 많아야 깊은 것이 아니라, **답변이 작업 방향을 바꿀 수 있는 질문**이어야 깊습니다.

## 5. 작업 기록은 “대화 로그”가 아니라 “추적 가능한 요구사항 기록”이어야 합니다

요구사항 도출 분야에서는 이해관계자, 문서, 시스템 등 요구사항의 출처를 식별·관리하고, 프로젝트 상황에 맞는 도출 기법을 적용하며, 요구사항 충돌을 분석·해결하고, 이해관계자 니즈에 맞는지 검증하는 구조적 접근을 강조합니다. ([CPRE][4])

따라서 AI의 작업 기록도 다음처럼 저장하는 것이 좋습니다.

```json
{
  "task_id": "proposal_2026_001",
  "explicit_request": "신제품 제안서 작성",
  "inferred_intent": [
    {
      "need": "내부 승인용 문서가 필요함",
      "evidence": "사용자가 '대표님께 보고'라고 언급",
      "confidence": 0.82,
      "status": "confirmed"
    }
  ],
  "audience": {
    "value": "대표이사 및 사업부장",
    "source": "user_answer",
    "confidence": 1.0
  },
  "success_criteria": [
    {
      "criterion": "1페이지 안에서 시장성, 비용, 일정이 판단 가능해야 함",
      "source": "user_answer"
    }
  ],
  "constraints": [
    {
      "type": "format",
      "value": "A4 1페이지",
      "source": "user_answer"
    },
    {
      "type": "tone",
      "value": "컨설팅 보고서 톤",
      "source": "user_answer"
    }
  ],
  "assumptions": [
    {
      "assumption": "재무 수치는 추정치로 표기한다",
      "confidence": 0.6,
      "needs_confirmation": true
    }
  ],
  "open_questions": [
    "예상 매출 수치의 출처 확인 필요"
  ],
  "decisions": [
    {
      "decision": "보고서는 문제-기회-제안-효과-리스크 구조로 작성",
      "made_by": "assistant",
      "confirmed_by_user": false
    }
  ]
}
```

중요한 점은 `inferred_intent`와 `confirmed_requirement`를 분리하는 것입니다. 숨은 니즈는 어디까지나 **가설**이고, 사용자가 확인하기 전까지는 확정 사실로 저장하면 안 됩니다.

## 6. 프롬프트는 이렇게 설계할 수 있습니다

아래는 AI 모델에게 부여할 수 있는 시스템 프롬프트 예시입니다.

```text
너는 사용자의 작업 의도를 도출하고 작업 기록을 정교화하는 Socratic Requirements Analyst다.

목표:
- 사용자의 명시 요청과 암묵 니즈를 구분한다.
- 숨은 니즈는 단정하지 말고 가설로 기록한다.
- 필요한 경우에만 논리학적 질문을 한다.
- 질문은 사용자의 부담을 줄이면서 작업 결과에 큰 영향을 주는 것부터 묻는다.
- 답변을 받은 뒤 작업 기록을 갱신한다.

매 턴 절차:
1. 사용자의 발화를 다음 항목으로 분석한다:
   - explicit_request
   - likely_intent
   - audience
   - output_format
   - success_criteria
   - constraints
   - assumptions
   - risks
   - open_questions

2. 불확실성이 높은 항목을 찾는다.

3. 다음 기준으로 질문 후보를 평가한다:
   - 답변이 결과물을 바꾸는가?
   - 잘못 이해하면 리스크가 큰가?
   - 사용자가 쉽게 답할 수 있는가?
   - 지금 묻지 않으면 나중에 비용이 커지는가?

4. 질문이 필요한 경우:
   - 최대 3개만 묻는다.
   - 질문의 이유를 짧게 설명한다.
   - 가능하면 선택지를 제공한다.
   - 사용자를 추궁하는 ‘왜요?’ 대신 목적·근거·성공 기준을 묻는다.

5. 질문이 필요하지 않은 경우:
   - 합리적 가정을 명시하고 바로 작업한다.
   - 결과물 말미에 “확인 필요 사항”을 남긴다.

6. 사용자의 답변을 받은 뒤:
   - 확정된 요구사항
   - 여전히 남은 가정
   - 변경된 우선순위
   - 다음 작업
   으로 작업 기록을 업데이트한다.

출력 형식:
- 사용자에게는 자연스러운 대화로 응답한다.
- 내부 기록은 JSON 또는 표 형태로 유지한다.
```

OpenAI의 프롬프트 엔지니어링 문서도 프롬프트 엔지니어링을 “모델이 요구사항을 일관되게 충족하도록 효과적인 지시를 작성하는 과정”으로 설명하고, 복잡한 애플리케이션에서는 프롬프트 동작을 측정할 테스트와 평가 체계를 만들 것을 권장합니다. ([OpenAI Developers][5])

## 7. 실제 대화 예시는 이렇게 됩니다

사용자:

> “우리 서비스 소개자료 좀 만들어줘.”

나쁜 질문 방식:

> “무슨 서비스인가요? 누구에게 보여주나요? 분량은요? 디자인은요? 목적은요? 언제까지 필요하세요?”

이 방식은 질문이 많지만 구조가 없습니다.

좋은 질문 방식:

> “소개자료의 방향이 크게 달라질 수 있어서 세 가지만 확인하겠습니다.
>
> 1. 이 자료는 투자자 설득용, 고객 영업용, 내부 공유용 중 어디에 가깝나요?
> 2. 보는 사람이 자료를 읽고 어떤 결정을 내려야 하나요?
> 3. 완성 형태는 1페이지 요약, 발표용 슬라이드, 상세 제안서 중 무엇이 좋을까요?”

사용자가 답변:

> “고객 영업용이고, 미팅 전에 우리 서비스를 이해하게 만드는 게 목적이에요. 발표용 슬라이드 5장 정도면 좋겠어요.”

AI의 작업 기록 갱신:

```json
{
  "explicit_request": "서비스 소개자료 작성",
  "confirmed_intent": "고객 영업 미팅 전 사전 이해를 돕는 발표자료",
  "audience": "잠재 고객",
  "output_format": "5장 내외 발표용 슬라이드",
  "success_criteria": [
    "고객이 서비스의 핵심 가치와 적용 상황을 빠르게 이해함",
    "영업 미팅에서 상세 논의로 자연스럽게 이어짐"
  ],
  "remaining_questions": [
    "고객 산업군",
    "서비스 핵심 기능",
    "경쟁사 대비 차별점",
    "원하는 톤앤매너"
  ]
}
```

그다음 질문:

> “이제 내용 정확도를 위해 한 가지만 더 확인하겠습니다. 이 자료의 잠재 고객은 어떤 산업군 또는 직무인가요? 예: 제조업 운영팀, B2B SaaS 마케팅팀, 병원 행정팀 등.”

이런 식으로 질문이 점점 좁혀져야 합니다. 처음부터 모든 정보를 캐묻지 않고, **작업 방향을 결정하는 질문 → 내용 정확도를 높이는 질문 → 품질을 다듬는 질문** 순서로 진행합니다.

## 8. 추천 운영 구조

실제 제품이나 워크플로우로 만든다면 다음 구조가 좋습니다.

```text
User Message
   ↓
Intent Parser
   - 명시 요청 추출
   - 암묵 니즈 가설 생성
   - 누락 정보 탐지
   ↓
Question Planner
   - 소크라테스식 질문 후보 생성
   - 정보 가치 평가
   - 질문 수 제한
   ↓
Dialogue Manager
   - 질문할지, 가정하고 진행할지 결정
   ↓
Work Record Updater
   - 확정 요구사항
   - 가정
   - 열린 질문
   - 결정 기록
   - 출처와 신뢰도 저장
   ↓
Task Executor
   - 문서 작성
   - 분석
   - 코드 생성
   - 기획안 작성 등
```

여기서 가장 중요한 모듈은 `Question Planner`와 `Work Record Updater`입니다. 대부분의 AI 시스템은 답변 생성에는 강하지만, “어떤 질문을 해야 하는지”와 “답변을 어떻게 요구사항 기록으로 바꿀지”가 약하기 때문입니다.

## 9. 질문 유형을 작업 단계별로 배치하세요

| 작업 단계  | AI가 해야 할 질문                            | 목적       |
| ------ | -------------------------------------- | -------- |
| 착수     | “이 작업의 최종 사용처는 무엇인가요?”                 | 목적 확인    |
| 범위 설정  | “이번 산출물에 포함하지 말아야 할 것은 무엇인가요?”         | 과업 경계 설정 |
| 독자 설정  | “결과물을 볼 사람은 어떤 배경지식을 갖고 있나요?”          | 설명 수준 결정 |
| 기준 설정  | “어떤 결과가 나오면 성공인가요?”                    | 품질 기준 설정 |
| 제약 파악  | “분량, 형식, 톤, 기한 중 고정된 조건이 있나요?”         | 실행 조건 확정 |
| 가정 검증  | “제가 A라고 이해했는데 맞나요?”                    | 오해 방지    |
| 대안 탐색  | “A 방식 대신 B 방식도 가능한데, 어느 쪽이 목적에 더 맞나요?” | 선택지 비교   |
| 리스크 확인 | “잘못 표현되면 문제가 될 민감한 부분이 있나요?”           | 안전성 확보   |
| 최종 확인  | “제가 이해한 작업 조건은 다음과 같습니다. 맞으면 진행하겠습니다.” | 합의 형성    |

## 10. 평가 기준도 함께 만들어야 합니다

이 시스템이 잘 작동하는지 보려면 다음 지표를 봐야 합니다.

| 평가 항목  | 측정 질문                                |
| ------ | ------------------------------------ |
| 질문 효율  | 평균 몇 개의 질문으로 충분한 의도 파악이 되는가?         |
| 의도 정확도 | 최종 산출물이 사용자의 실제 목적과 얼마나 일치하는가?       |
| 재작업률   | 사용자가 “아니, 그게 아니라…”라고 수정하는 빈도가 줄었는가?  |
| 기록 품질  | 요구사항, 가정, 결정, 열린 질문이 분리되어 저장되는가?     |
| 사용자 부담 | 사용자가 질문을 귀찮게 느끼지 않는가?                |
| 추적성    | 특정 산출물의 근거가 어떤 사용자 답변에서 왔는지 추적 가능한가? |

프롬프트만 잘 쓰는 것으로 끝내지 말고, 실제 대화 샘플을 모아 “질문 수, 재작업률, 사용자 만족도, 요구사항 누락률”을 평가해야 합니다. 복잡한 AI 애플리케이션에서는 테스트와 평가 체계를 두고 프롬프트 동작을 모니터링하라는 권고와도 같은 방향입니다. ([OpenAI Developers][5])

## 결론

사용자의 숨겨진 니즈를 파악하는 AI를 만들려면, 접근은 이렇게 잡는 것이 가장 안정적입니다.

**질문법은 소크라테스식으로, 기록 방식은 요구사항 공학처럼, 실행 방식은 대화형 에이전트처럼 설계**해야 합니다.

즉 AI에게 단순히 “사용자 의도를 질문해서 파악해”라고 지시하지 말고, 다음 네 가지를 명시적으로 부여해야 합니다.

1. 어떤 의도 항목을 채워야 하는지에 대한 `Intent Frame`
2. 어떤 논리 기능의 질문을 사용할지에 대한 `Question Taxonomy`
3. 질문할지 실행할지 판단하는 `Question Policy`
4. 답변을 요구사항·가정·결정·열린 질문으로 저장하는 `Work Record Schema`

이렇게 만들면 AI는 사용자의 말을 단순히 “응답”하는 수준을 넘어, 사용자의 목적·맥락·제약·성공 기준을 점진적으로 밝혀내는 협업 파트너처럼 동작할 수 있습니다.
