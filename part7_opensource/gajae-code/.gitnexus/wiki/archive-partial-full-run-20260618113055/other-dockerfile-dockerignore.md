# Dockerfile.dockerignore

`Dockerfile.dockerignore` defines the Docker build context exclusions for the pi-root `Dockerfile`, which builds the `gajae-code/pi:dev` image.

This file is declarative: it has no functions, classes, imports, call graph edges, or runtime execution flow. Its behavior is applied by Docker before the build starts, when Docker decides which repository files are sent into the build context.

## Purpose

The file keeps the pi-root Docker build context small, deterministic, and safe by excluding:

- Large local build artifacts such as `target/`, `dist/`, and `runs/`
- Dependency directories such as `**/node_modules`
- per-host workspace state such as `.fallow/`, `.worktrees/`, `.wt/`, `.opencode/`, `.pi_config/`, and `.gjc/plugins/`
- VCS and editor churn such as `.git/`, `.vscode/`, `.zed/`, and `.idea/`
- generated files that the image build regenerates
- logs, profiler outputs, test artifacts, scratch files, and secrets

The most important exclusion is `target/`; the file notes that this directory alone can exceed 100 GB on a development machine and must never be sent to Docker.

## How Docker Uses This File

`Dockerfile.dockerignore` is a Dockerfile-specific ignore file. It applies to the pi-root `Dockerfile` and shadows the repository-level `.dockerignore` for that Dockerfile only.

The repository also has a separate Robogjc build surface:

- `Dockerfile.robogjc`
- `Dockerfile.robogjc.dockerignore`

Do not add Robogjc-specific exclusions here unless they also apply to the pi-root `Dockerfile` build context.

## Exclusion Groups

### Heavy Build Outputs

```dockerignore
target/
**/node_modules
dist/
runs/
```

These paths are excluded because they are large, generated, or host-specific. They should not affect image reproducibility and can make Docker context transfer extremely slow.

`**/node_modules` excludes dependency folders at any nesting depth.

### Local Agent and Worktree State

```dockerignore
.fallow/
.worktrees/
.wt/
.opencode/
.pi_config/
.gjc/plugins/
```

These directories are local runtime state for parallel agents, worktrees, local configuration, or plugin installs. They are not source inputs for the image build.

`.gjc/plugins/` is intentionally excluded because installed local plugins are runtime/user state, not bundled source.

### VCS and Editor State

```dockerignore
.git/
.npm/
.vscode/
.zed/
.idea/
```

These paths churn frequently and are irrelevant to the Docker image. Excluding `.git/` also prevents repository metadata from becoming part of the build context.

### OS and Temporary Files

```dockerignore
.DS_Store
*.swp
*.swo
*~
*.tmp
```

These patterns remove platform noise and editor swap files.

### Logs and Profiling Artifacts

```dockerignore
*.log
*.cpuprofile
*.heapprofile
*.heapsnapshot
CPU.*
```

These files may be large, transient, or sensitive. They are not valid build inputs.

### Build and Test Side Outputs

```dockerignore
*.tsbuildinfo
coverage/
.nyc_output/
__pycache__/
compaction-results/
changes/
```

These are generated by TypeScript, test coverage tools, Python, and local analysis workflows. The Docker image should build from source, not cached local outputs.

### Regenerated Files

```dockerignore
packages/coding-agent/src/internal-urls/docs-index.generated.ts
packages/natives/native/.build/
packages/natives/native/pi_natives.darwin-*.node
packages/natives/native/pi_natives.dev.node
packages/ai/test/.temp-images/
python/gjc-rpc/src/gjc_rpc.egg-info/
python/robogjc/data/
python/robogjc/.cache/
python/robogjc/src/robogjc/static/
python/robogjc/web/dist/
```

These files are generated or cache-like outputs. The in-image build is expected to regenerate the relevant artifacts rather than copying host-generated versions.

This is especially important for native binaries such as:

```dockerignore
packages/natives/native/pi_natives.darwin-*.node
packages/natives/native/pi_natives.dev.node
```

Those files are host/platform-specific and should not leak into a Linux image build.

### Scratch Files

```dockerignore
syntax.jsonl
out.jsonl
out.html
pi-*.html
```

These are ad-hoc files created during local development or debugging. They are excluded to keep the build context predictable.

### Secrets

```dockerignore
.env
```

`.env` must never be included in the Docker image or sent to the Docker daemon as build context.

## Maintenance Guidance

When adding a new generated directory or local cache, prefer excluding it here if it is not required by the pi-root `Dockerfile` build.

Before adding a pattern, check whether the file is:

- required by the Dockerfile during `COPY`
- generated inside the image build
- host-specific or platform-specific
- potentially large
- potentially secret-bearing
- specific to Robogjc rather than the pi-root image

Do not exclude source files, package manifests, lockfiles, build scripts, or static assets that the pi-root `Dockerfile` needs to reproduce the image.

## Common Pitfalls

A missing exclusion can cause slow builds because Docker sends the entire build context before executing Dockerfile steps.

An overly broad exclusion can break the image if a later `COPY` instruction expects that file to exist in the context.

Generated native files are especially risky: copying a local `.node` binary into an image can produce platform mismatches that only fail at runtime.

`.env` should stay excluded even if a local build appears to need it. Runtime configuration belongs in environment injection, not in the image build context.
