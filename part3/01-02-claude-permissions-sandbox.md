# Session 1-2. Claude Code 권한과 샌드박스 실전 설정

## 목표

Claude Code의 권한 설정을 복사해서 쓰는 것이 아니라, settings 파일의 위치, 우선순위, 권한 규칙을 자기 프로젝트에 맞게 설계하는 법을 익힌다.

## 준비물

- Claude Code settings 공식 문서
- Claude Code hooks 공식 문서
- 실습용 프로젝트

## 진행 순서

1. 설정 위치와 우선순위를 확인한다.
   - 사용자 전역 설정
   - 프로젝트 공유 설정
   - 개인 로컬 설정
   - 조직 관리 정책이 있는 경우의 차이

2. 권한 규칙을 작업 언어로 읽는다.
   - 어떤 도구를 허용할 것인가
   - 어떤 도구는 매번 물어볼 것인가
   - 어떤 파일과 명령은 거부할 것인가
   - 추가 디렉터리 접근이 필요한 경우 어떻게 제한할 것인가

3. 민감 파일 차단을 먼저 다룬다.
   - `.env`, 인증 키, 운영 설정, 고객 데이터 파일은 기본적으로 읽지 못하게 하는 쪽을 권장한다.
   - "AI가 알아서 조심한다"가 아니라 설정으로 막는 것이 운영 기준이다.

4. strict, medium, loose 설정을 비교한다.
   - strict: 사내 코드·운영 데이터 근처에서 읽기만 자동, 쓰기는 승인, 파괴·외부 호출은 거부
   - medium: 일반 업무 코드에서 안전한 읽기·쓰기·검증은 자동, 외부 영향 명령은 승인
   - loose: 개인 실습·격리 샌드박스에서만 사용

5. hooks는 검증 루프의 보조 장치로 소개한다.
   - 알림, 차단, 검증 명령 실행부터 시작한다.
   - 자동 수정 hook은 의도치 않은 diff를 만들 수 있으므로 별도 승인 대상으로 둔다.

## 데모/실습

실습용 프로젝트에서 "읽기는 허용, 수정은 승인, 민감 파일은 거부" 정책 초안을 만든다. 먼저 1-1에서 만든 매트릭스를 보고 strict/medium/loose 중 어디서 시작할지 고른다.

```text
Claude Code 권한 정책 초안을 만들어줘.
목표는 일반 코드 읽기와 테스트 실행은 편하게 하되, .env, secrets, 배포 명령, git push는 사람 승인을 거치게 하는 것이다.
공식 문서에서 확인해야 할 항목과 적용 전 주의사항도 함께 적어줘.
```

## Windows/WSL 주의

- Windows와 WSL에서 경로 표기와 실행되는 셸이 다를 수 있다.
- native Windows에서 동작하는 명령과 WSL 내부에서 동작하는 명령을 섞어 쓰지 않도록 현재 셸을 먼저 확인한다.

## 산출물

Claude Code 권한 정책 초안:

```text
허용할 작업:
승인받을 작업:
금지할 작업:
민감 파일 패턴:
검증 명령:
우회가 필요한 예외 상황:
촬영일 기준 재확인할 공식 문서:
```

## 완료 기준

수강생이 Claude Code 설정을 자기 프로젝트의 위험도에 맞춰 설계하고, 적용 전 공식 문서와 로컬 설정을 확인할 수 있어야 한다.

## 촬영 전 확인

- deny 패턴을 너무 넓게 잡아 정상 작업까지 막히는 실패 예시를 하나 준비한다.
